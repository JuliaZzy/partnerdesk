KA Account Agent 后端路由图

HTTP 层只有 app.py 一个文件，下面全是不认识传输层的 service.py 和领域模块。 一个聊天入口，router 分流给 specialist；每个数字、每个判定都在代码里，模型只出现在紫色节点上。

4. 订单 specialist：确认门 po/turn.confirm_order

flowchart TD
  CLICK(["POST /confirm，带着图 3 ⑥ 存下的 token
是按钮，不是推断"]) --> TOK{{"token 对得上？没过期？"}}
  TOK -->|"否"| USED["used / expired

  TOK -->|"是"| RECHECK["重跑 run_code_check
live 目录 + live 规则 · 不调模型"]
  RECHECK --> SAME{{"draft hash 没变？"}}
  SAME -->|"变了"| CHANGED["changed：退回 gathering
让用户重看新草稿"]
  SAME -->|"没变"| BURN["db.burn_confirm_token
原子 UPDATE，建单之前先烧"]
  BURN -->|"没烧到：双击 / 重试"| USED
  BURN -->|"烧到了"| SUBMIT["po/submit.create_and_submit_po
折扣、总价由代码算"]
  SUBMIT --> T_PO[("purchase_orders · purchase_order_items
po_rule_evaluations · po_events")]

  class CLICK human
  class TOK,USED,RECHECK,SAME,CHANGED,BURN,SUBMIT code
  class T_PO db
  • 确认门里没有模型：会话里的 slots 已经由对话定下来，点击时再抽取一遍等于让模型重新决定用户已经看过的订单。
  • 重跑校验并比对 hash——这期间价格或规则变了就不建单，返回 changed 让用户重看。
  • 先烧 token 再建单：两次点击相隔一秒，一个 UPDATE 命中，另一个什么都没命中、直接返回 used——双击只产生一张订单。
